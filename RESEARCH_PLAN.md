# Research Plan

## Goal

Investigate whether a quantum programming representation designed for LLM generation can improve functional correctness and reduce framework-specific overhead.

The central idea is to move setup, API conventions, imports, execution plumbing, and other framework-specific machinery out of the LLM-generated program and into the language/compiler/runtime, allowing the model to focus more directly on the quantum programming task.

## Research Questions

1. Which quantum programming tasks are representative enough to evaluate an LLM-oriented language?
2. How much non-semantic overhead do existing frameworks expose to the LLM?
3. Can an existing representation such as OpenQASM already provide the properties we want?
4. If not, what language design choices reduce generation overhead while preserving expressiveness?
5. Does the resulting representation improve functional correctness, token efficiency, and repairability across models?

## Plan

### 1. Select benchmark tasks

Start from **Qiskit HumanEval (QHE)**, but keep only tasks whose core objective can be described independently of Qiskit.

Prefer tasks involving state preparation, parameterized circuits, gate composition/decomposition, oracles, common quantum algorithms, measurement, and quantum protocols.

Exclude tasks that primarily test knowledge of Qiskit-specific APIs, visualization, transpiler internals, serialization, or backend objects.

**Deliverable:** a small benchmark suite with neutral, framework-independent task descriptions.

### 2. Characterize framework overhead

Implement the selected tasks in:

- Qiskit
- PennyLane
- Cirq
- OpenQASM, where applicable

Separate code needed for the quantum computation from code needed for imports, circuit construction, API conventions, execution, transpilation, result extraction, and other boilerplate.

Measure total token count and framework-specific overhead.

### 3. Evaluate existing representations

Before creating a new language, determine whether an existing representation such as OpenQASM already removes enough overhead.

Compare candidates on:

- compactness
- canonicality
- expressiveness
- ease of validation
- required framework knowledge
- number of equivalent ways to express the same operation

### 4. Define language requirements

If existing representations are insufficient, derive the language design from the benchmark and framework analysis rather than inventing syntax first.

Likely goals include:

- one clear representation for each operation
- explicit qubit operands
- minimal boilerplate
- no imports or library-specific setup
- predictable measurement semantics
- compact parameter handling
- easy parsing and static validation
- a small specification that fits comfortably in model context

### 5. Build the language and compiler/runtime

Target pipeline:

```text
Natural-language task
        ↓
       LLM
        ↓
Quantum representation
        ↓
      Parser
        ↓
 Validation / AST
        ↓
  Backend lowering
   ↙     ↓      ↘
Qiskit  Cirq  OpenQASM
        ↓
     Execution
```

Framework-specific setup and execution should be handled by the compiler/runtime rather than generated by the LLM.

### 6. Run pilot experiments

Compare the same tasks across:

- Qiskit with normal scaffolding
- Qiskit without scaffolding
- other framework representations
- OpenQASM
- the proposed representation

Start with at least one reproducible open-weight model and one strong frontier model.

### 7. Evaluate results

**Primary metric**

- functional correctness / Pass@k

**Secondary metrics**

- generated token count
- parse/compile success rate
- repair success and number of repair attempts
- circuit depth / gate count where relevant
- framework/API error rate
- quantum-reasoning error rate

Classify failures so we can distinguish representation improvements from improvements in actual quantum reasoning.

### 8. Run language ablations

If the proposed representation helps, vary individual features to identify which design choices matter.

Examples:

- canonical vs. multiple equivalent syntaxes
- explicit vs. implicit measurement
- compact vs. verbose gate notation
- restricted vs. general control flow
- different parameter conventions

The goal is to explain *why* a representation is easier for LLMs, not only show that one syntax performs better.

## Working Hypothesis

Moving framework-specific implementation burden from generated code into language/compiler semantics will improve LLM quantum-program generation by reducing API/setup errors and allowing more of the model's generation budget to represent the intended quantum computation.

Token efficiency is useful, but the primary outcome is **functional correctness**.
